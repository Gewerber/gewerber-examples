# Self-hosted Gewerber backend (standalone OSS, single-tenant)

Minimal Docker Compose stack for running the open-source
[Gewerber backend](https://github.com/Gewerber/gewerber-backend) on your
own server: **Serverpod API server + PostgreSQL 16 (+ Redis)**, no reverse
proxy, no deploy tooling. One instance serves one organization (single-tenant).

> Open-core only: this example covers the OSS modules (invoicing, time
> tracking, basic accounting, guidance). Closed modules (banking, tax/ELSTER,
> employees, subscriptions, AI assistant) are not part of it.
>
> **Caveat on the prebuilt image.** The default `image:` is the CI release image
> `ghcr.io/gewerber/gewerber-backend:prod-latest`, which is built by the
> commercial pipeline and therefore **contains the closed commercial module**
> (its endpoints stay inert without a commercial license, but the code is in the
> image). A genuinely OSS-only artifact is only produced by building from source
> with `REQUIRE_COMMERCIAL=false` — see "Building an OSS-only image" below.

## How this differs from the production deployment

The full production setup lives in the backend repo:
[`deploy/docker-compose.yml`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/docker-compose.yml)
(+ [`.env.example`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/.env.example),
[`deploy.sh`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/deploy.sh),
[runbook](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/README.md)).
It runs behind Traefik with TLS, resource limits and per-environment secret
generation.

This example is a stripped-down variant of that file:

| | Production (`deploy/`) | This example |
|---|---|---|
| TLS / reverse proxy | Traefik (labels in compose) | none — plain HTTP port published; put your own proxy in front or keep it on a trusted LAN |
| Exposed ports | 8080 via Traefik only | `${SERVER_PORT:-8080}` published directly (Insights 8081 stays internal) |
| Resource limits | `deploy.resources.limits` on all services | none — add your own if needed |
| Secrets | generated by `deploy.sh` | you generate them yourself (below) |
| Service names / DB name | `server`, `postgres`, `redis` / `gewerber_backend` | identical — upstream `backup.sh`/`restore.sh` work unchanged |

## Prerequisites

- Docker Engine + Compose plugin
- Ports: one free TCP port (default 8080)

## Quickstart

### 1. Create the secrets file

Serverpod reads its secrets at runtime from `config/passwords.yaml`, which is
**not** baked into the image and is **not** in version control. Create it once:

```bash
cd self-hosted
mkdir -p config
```

Generate the required values and fill them into the template below:

```bash
openssl rand -base64 32   # database password      -> passwords: production.database
openssl rand -base64 32   # service secret         -> serviceSecret
openssl rand -base64 32   # email pepper           -> emailSecretHashPepper
openssl rand -base64 64   # JWT private key        -> jwtHmacSha512PrivateKey
openssl rand -base64 32   # refresh token pepper   -> jwtRefreshTokenHashPepper
```

`config/passwords.yaml` (minimal template):

```yaml
production:
  database: <DB_PASSWORD>
  serviceSecret: <SERVICE_SECRET>
  emailSecretHashPepper: <EMAIL_PEPPER>
  jwtHmacSha512PrivateKey: <JWT_PRIVATE_KEY>
  jwtRefreshTokenHashPepper: <REFRESH_PEPPER>
```

Keep `<DB_PASSWORD>` consistent with `DB_PASSWORD` you set in `.env`
(step 2) — it must match `POSTGRES_PASSWORD`. SMTP keys are optional; without
them verification codes are logged instead of emailed (see the upstream
[runbook](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/README.md)).

> ⚠️ Disclaimer: `config/passwords.yaml` contains all server secrets and is
> mounted read-only into the container at `/app/config/passwords.yaml`. Never
> commit it, never share it. Rotating any value invalidates existing sessions.

### 2. Configure the environment

```bash
cp .env.example .env
```

Edit `.env`: set `DB_PASSWORD` to the same value as `database:` above,
generate `REDIS_PASSWORD`, adjust port/name if needed.

### 3. Start the stack

```bash
docker compose up -d
```

Migrations are applied automatically on first start
(`SERVERPOD_APPLY_MIGRATIONS=true`). Watch startup with
`docker compose logs -f server`.

### 4. Verify health

```bash
docker compose ps                 # all services healthy after ~30 s
curl http://localhost:8080/readyz # readiness probe used by the healthcheck
curl http://localhost:8080/livez  # liveness
```

The API is now reachable from your network as plain HTTP — do not expose it
to the public internet without putting a TLS-terminating reverse proxy in
front.

## Updating

```bash
docker compose pull server
docker compose up -d
```

New migrations apply automatically on container start.

## Backups & restore

Reuse the upstream scripts unchanged — they operate on whatever directory you
point `DEPLOY_DIR` at, as long as it contains a `docker-compose.yml` with
services named `postgres`/`server` and a database named `gewerber_backend`
(all true here):

```bash
git clone https://github.com/Gewerber/gewerber-backend.git
DEPLOY_DIR="$PWD" BACKUP_DIR="$HOME/gewerber/backups" \
  bash gewerber-backend/deploy/backup.sh prod

DEPLOY_DIR="$PWD" \
  bash gewerber-backend/deploy/restore.sh "$HOME/gewerber/backups/gewerber_backend_<stamp>.dump" prod
```

- [`backup.sh`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/backup.sh) — `pg_dump -Fc` + integrity check + retention pruning; schedule via cron.
- [`restore.sh`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/restore.sh) — verified, confirmed, destructive restore (stops/restarts the API server itself).
- Runbook with RPO/RTO guidance: [`deploy/README.md`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/README.md).

Ship backups off-box — a dump on the same disk as the database is not a
disaster-recovery copy.

## Building an OSS-only image

The release pipeline builds with private access to `gewerber-backend-commercial`,
so `prod-latest` is not an OSS-only artifact (see the caveat at the top). To
build one yourself, clone
[`gewerber-backend`](https://github.com/Gewerber/gewerber-backend) next to this
repository and replace the `image:` line in `docker-compose.yml` with:

```yaml
    build:
      context: ../../gewerber-backend
      dockerfile: gewerber_backend_server/Dockerfile
      args:
        # No private access -> resolve the public stub module. The Dockerfile
        # defaults to REQUIRE_COMMERCIAL=true and FAILS in that case, so this
        # opt-out must be explicit.
        REQUIRE_COMMERCIAL: "false"
        GEWERBER_DEP_REF: main
```

The image build prints which module package it resolved; with
`REQUIRE_COMMERICAL=false` a stub resolution is a warning rather than a failure.
The resulting image is functionally the OSS core: the commercial endpoints are
absent instead of present-but-inert.

## Notes

- **Redis**: kept because the prebuilt image's config references it, but the
  application code does not use Redis today — see the "Redis" audit section in
  the upstream
  [`deploy/README.md`](https://github.com/Gewerber/gewerber-backend/blob/main/deploy/README.md)
  for when it can be dropped (requires building your own image).
- **Invoice PDF font**: the invoice fallback font lives at the CWD-relative
  path `assets/fonts/Roboto-Regular.ttf` inside the image. Changing the
  container `WORKDIR` or mounting a volume over `/app` breaks that lookup and
  silently degrades generated PDFs to glyph-limited Helvetica (no `€` or `–`).
  The resolved font path is logged when the font is first loaded (once per
  process, on the first generated invoice) — use that line to diagnose, and
  point the server at the right file via the `GEWERBER_INVOICE_FONT_PATH`
  environment variable if you must override it.
- **Multi-tenancy**: the OSS core is built multi-tenant, but this standalone
  example targets a single organization hosting its own instance.
